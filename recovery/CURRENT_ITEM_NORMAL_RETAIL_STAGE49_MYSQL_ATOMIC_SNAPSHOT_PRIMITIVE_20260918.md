## Confirmed pre-existing persistence split

Current `server/cmd/protocol-probe/main.go` selects MySQL only when `NINEYIN_MYSQL_DSN` is set and migration succeeds; otherwise it opens legacy JSON stores. `zz_recovered_overlay.go` `mysqlBagStore.Save` (approx lines 3483 onward) independently begins a SQL transaction, deletes the role's `role_bag_items` snapshot, reinserts rows and commits. `mysqlCurrencyStore.Save` (approx lines 501 onward) independently begins another SQL transaction, deletes/inserts the role's JSON `role_currency.snapshot` and commits. JSON mode writes `data/bag_items.json` using temp+rename but writes `data/currency.json` separately with `os.WriteFile`; neither mode previously offered one atomic normal-purchase write. The normal buy handler at approx lines 6470–6565 changes actor currency, adds a bag item, writes client frames, then invokes those two separate stores; persistence errors can be logged without rolling back actor or client display.

## New production-code primitive, deliberately not wired into buy handler

New `server/cmd/protocol-probe/latest_client_normal_shop_mysql_atomic.go` defines `normalShopCommitMySQLSnapshots(ctx, db, roleID, beforeCurrency, afterCurrency, beforeBag, afterBag)`. It uses **one `sql.Tx`** to lock the existing `role_currency` snapshot with `SELECT ... FOR UPDATE`, compare its four existing currency fields against the caller's pre-state, lock existing bag rows and compare all 10 fields persisted by `mysqlBagStore.Save` in sequence, delete/insert the proposed bag snapshot, `UPDATE` the existing currency snapshot, then commit. Empty/missing currency rows, stale actor-versus-disk balances or bag contents, invalid new bag row, query/write errors reject the transaction. The deferred rollback runs on pre-commit failure. `RowsAffected=0` on an existing locked row is allowed because MySQL may report changed rows rather than matched rows for an unchanged snapshot; the prior `SELECT ... FOR UPDATE` establishes that the row exists.

**Boundaries:** This primitive does not infer a sale price, stack limit, network packet, GM grant, or exchange settlement. It does **not** call or replace the live `handleShopBuyCustom` yet; it does **not** mutate `playerActor` or send client frames. It cannot make legacy JSON files atomic; it rejects missing DB/role rather than silently falling back. It requires the future caller to assemble accurate pre/post actor snapshots under suitable serialization, pre-encode client frames, validate shop selection, item catalog/stack/slot constraints, and update actor/client **only after** a confirmed DB commit. A commit-returned error can be ambiguous if the connection fails after the database commits; no exactly-once request identifier or reconciliation strategy has yet been established. Other legacy writers still use independent `Save` calls, so serializability of all concurrent gameplay changes is not proven. Recreated/incomplete MySQL schema and initial unpersisted currency must be handled explicitly, not by inventing values.
