## Changes committed

New `server/cmd/protocol-probe/latest_client_normal_shop_atomic_buy.go` (staged commit `5be3742ffebf3bc1230b1e5cf70c782f25714869`) implements `normalShopAtomicBuy`. Both actual normal-buy 0x46 routes in `server/cmd/protocol-probe/main.go` (scene and activity dispatch) now pass the actual scene lifecycle and equipment catalog; `handleShopBuyCustom` in `zz_recovered_overlay.go` delegates to the new guarded implementation. The limited production integration commit is [`840c291e73bbd9a9cd510153c233027b2df0ee6c`](https://github.com/kim8553/web/commit/840c291e73bbd9a9cd510153c233027b2df0ee6c). Its diff changes **only main.go and zz_recovered_overlay.go**; existing Stage49 SQL primitive and GM/0x4F implementation were not modified.

Normal-buy request rejects malformed field types, missing player or role, shop mismatch with the current live NPC shop selection, unsupported listing modes, invalid price, unknown catalog item, invalid item category/type, insufficient money, full/inconsistent bag and JSON/nonmatching-DB stores. Initial integration accepts **count exactly 1**, avoids guessing stack/quantity grant semantics, and uses a vacant slot in the existing advertised `BaseCap` only (not the larger structural view capacity). It pre-encodes current-client bag and currency frames; takes `player.mu` to snapshot and calculate before/after state, performs Stage49 `normalShopCommitMySQLSnapshots` with **one SQL transaction** for bag and currency, changes in-memory actor only after a successful commit, then writes frames to client. A transaction error disconnects this session rather than continuing with potentially stale actor state; a post-commit client frame error also forces reconnect. No unverified JSON fallback is attempted.

Stage50 pinned patch script `tools/stage50_normal_shop_atomic/apply_normal_shop_atomic_buy.py` pins the original Git blob SHAs `15568d3f43794eb78045a39655e1a4964b8fb736` (overlay) and `63f8de991249b40b4e95418ebcb497bdc070458a` (main), uniquely replaces the one normal-buy handler and precisely the two existing 0x46 dispatch calls. Guard workflow `.github/workflows/jiuyin-stage50-normal-shop-atomic-integration.yml` limits publication to those two tested changes.

## Remaining blockers and no success claims

**Not tested:** a running real MySQL instance; rollback/readback after injected real SQL error; the user's Windows server boot; current-client actual NPC opening, item purchase and bag/currency display; reconnect persistence; concurrent writes and duplicate/replayed requests; all items and quantities; normal sale 0x47; full Chinese/GBK names. The buyer's independent gameplay persistence paths (including logout deferred saves and bag move/use) still exist, so cross-handler serializability is **not proven**. The selected DB must have a valid initialized `role_currency` row and matching bag row layout; missing currency rows deliberately fail closed. Commit-error ambiguity and lack of request idempotency are unresolved; disconnect/reload is mitigation, not proof of exactly-once settlement. The initial BaseCap slot gate and known item catalog gate can reject otherwise valid purchases, and count >1 is intentionally blocked. Legacy JSON mode cannot guarantee a combined transaction and is blocked for normal purchasing; 0x4F remains blocked; GM grant untouched.

**Status:** ordinary 0x46 buyer has a **compiled, wired, MySQL-only single-item atomic-save path** backed by fake-driver transaction tests; **NOT live-verified or complete**. Ordinary seller 0x47 is still not implemented.

**Next single priority:** test this wired 0x46 path with a backed-up real MySQL fixture and current client, verifying initialized currency row, bag column compatibility, success, forced bag INSERT/currency UPDATE failure rollback, client view synchronization, disconnect/reconnect readback and competing legacy writers. Only expand quantity/items and implement 0x47 sale after actual sale payout/rules and persistence safety are demonstrated. Never invent sale prices or silently turn JSON purchases on.
