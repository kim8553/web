## 검증된 Go 로더 동작과 최소 수정

- `cmd/protocol-probe/shop_catalog.go`의 기존 규칙은 `PageInfo`의 비어 있지 않은 토큰 개수를 `pageCount`로, 숫자 상품 키를 0부터 시작하는 `page`로 해석한다. 기존에는 위 섹션에서 `pageCount=1`과 `page=1` 상품을 동시에 성공 반환했다.
- `shop_catalog_page_info_bounds_test.go`: 위 원본 섹션의 축약 없는 실제 행으로 새 테스트를 작성했다. 수정 전 **FAIL**: 두 상품을 성공 반환하고 `pageCount=1`. 수정 후 **PASS**: 상점 ID 및 `PageInfo`가 포함된 오류 반환. 한 페이지 및 두 페이지의 정상 행, `PageInfo`가 없는 경우의 기존 페이지 계산을 별도 테스트해 PASS.
- 코드 수정: 명시적 `PageInfo`가 있고 가장 큰 상품 페이지 키가 선언 페이지 수 이상이면 **해당 상점 섹션 전체를 로드 거부**한다. 원본 상품을 다른 페이지로 이동하거나 페이지 수를 임의로 늘리지 않으며, 가격·재화·SQL·패킷·로그인 경로는 건드리지 않는다.
- 실제 두 후보 모두 `Shop_special_001`이 검증 대상이므로 이 로더를 사용하는 경우 해당 상점은 표시되지 않을 수 있다. 이는 데이터 정정이나 실게임 상점 복원의 완료가 아니라, 로더가 모순된 입력을 성공으로 보고하지 않도록 하는 안전 수정이다.
- 수정 커밋 `3179cc483f360b007fa343f6fa372473125f7833`, 테스트 생성 커밋 `d3088a7a1361fc0369197df9ba25aa1035d96eee`. GitHub Actions 상점 검증 워크플로에 새 테스트를 추가한 커밋 `9b6bd36d8729947899ecfbaecc0694a1401b07a1`.

## 검증 한계 및 후속

합성 fixture의 Go 파서 테스트와 GitHub CI의 컴파일/Windows 빌드는 사용자 PC MySQL 또는 최신 클라이언트 실게임 테스트를 대체하지 않는다. PCK 색인의 정확한 경로→스트림 매핑은 여전히 미해결이며, 실제 NPC 구매·판매·재접속 유지도 미검증이다. PCK 매핑이 입증되기 전에는 두 스트림 중 하나를 선택하거나 기존 파일을 덮어쓰지 않는다. 판매 요청/정산 패킷을 추측해 구현하지 않는다.
